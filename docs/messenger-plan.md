# 메신저 — 기획안 v0.1 (2026-09-29, 사용자 결정 대기)

사용자 요청(2026-09-29): 「메신저는 사용자 이름을 기반으로 보여지고, 클릭하면 대화창을 열어 소통할 수 있으면 좋겠어」. 비서(tbox-buddy)에서 커뮤니티를 쓰는 이야기 중에 나온 요청이라 **웹(커뮤니티) + 비서** 둘 다 고려한다. 이 문서는 기획이다 — 사용자 결정(아래 「결정할 것」)이 나기 전에는 구현 지시서를 쓰지 않는다(CLAUDE.md 0장).

## 1. 한 줄 정의

로그인한 사람들의 **이름 목록**이 보이고, 이름을 누르면 그 사람과의 **1:1 대화창**이 열려 짧은 글을 주고받는다. 보낸 글은 저장되어 나중에 다시 볼 수 있고, 받은 사람에게 알림이 간다.

## 3. 선택지 — 「실시간」의 정도 (가장 큰 갈림길)

| 안 | 모습 | 비용 | 위험 |
|---|---|---|---|
| **A. 폴링(기본안)** | 대화창이 열려 있을 때 3~5초마다 새 글을 가져온다. 종은 30초 그대로 | 새 부품 0 · nginx·PHP-FPM 그대로 · 기존 알림 폴링과 같은 방식 | 「즉시」 는 아니다(최대 5초 늦음). 열린 대화창 수만큼 요청이 는다(사람 10명이면 무시할 수준) |
| B. SSE(서버 → 브라우저 한 방향 스트림) | 새 글이 1초 안에 뜬다 | PHP-FPM 워커가 연결마다 붙잡힌다 → 워커 수·nginx 버퍼링 설정 변경(7장 앱 밖 검토) | 워커 고갈로 **t-box 전체가 느려질 수 있다**. 10명 규모면 감당되지만 설정 실수 한 번이 사이트 장애 |
| C. WebSocket | 양방향 즉시 | PHP 밖에 별도 프로세스(새 외부 부품 — S-05 심사) · 인증 통로 하나 더 | 새 공격면 · DEPENDENCIES · 운영 부담. 지금 규모에 과하다 |

Fable 의견: **A**. 사내 10명 규모에서 5초 지연은 체감이 작고, 부품이 늘지 않는다. 뒤에 부족하면 B 로 올리는 길이 막히지 않는다(창구·표는 같고 「가져오는 방법」만 바뀐다).

## 4. 범위 선택지

| 항목 | 기본안 | 다른 선택 |
|---|---|---|
| 상대 | 1:1 만 | 팀 방(팀 공간과 짝) — 다음 판 |
| 본문 | 짧은 글(블록 JSON · 링크·멘션 허용 · 이미지는 t-box 파일 링크로) | 파일 첨부 직접 — t-box 올리기와 겹치니 링크로 대체 |
| 보관 | 지우지 않는다(댓글과 같음 · 보낸 사람이 「숨김」만 · 관리자 감사) | 기간 뒤 자동 삭제 — 운영 데이터 삭제 원칙(CLAUDE.md 4장)과 충돌, 권하지 않음 |
| 읽음 표시 | 「읽음 ✓」 상대에게 보임 | 없음(사생활) |
| 온라인 표시 | **없음**(세션 정보를 남에게 노출하지 않는다 — 누가 언제 접속했나는 관리자 감사 화면의 일) | 「최근 5분 활동」 점 — 세션 last_seen 노출이라 권하지 않음 |
| 알림 | 종 + 폰 브라우저 알림(이미 있는 푸시 부품 `deploy/push.conf` 가 있으면 그것) | 이메일 — 없음 |
| 비서 | 팔레트 「쪽지」: 이름 고르기 → 한 줄 보내기 · 새 쪽지는 트레이 풍선 | 비서 안 대화창 — 다음 판 |
| 손님(Guest) | 메신저 **없음**(직원 목록을 못 보는 규칙과 같이) | 관리자와만 — 필요하면 |

## 5. 보안 요구(초안 — 확정되면 SECURITY.md 에 C:R-xx 로)

- 이름 목록·대화 조회는 **SQL WHERE** 로 「내가 볼 수 있는 사람」·「내가 낀 대화」만(C:S-02). 대화 id 를 알아도 남의 대화는 404.
- 본문은 블록 JSON 만 · 출력은 렌더러(댓글과 같은 코드) · 링크는 기존 허용 목록.
- 보내기는 CSRF · 속도 제한(분당 n건 — 값은 결정) · 감사 `message.send`(본문 없이) · 경보 AL-x(한 사람이 10분에 100건 같은 남용).
- 토큰 출신 세션(Q:F-9)에서 쪽지 보내기는 재인증 **없음**(일반 쓰기와 같은 등급) — 결정 가능.
- 관리자가 남의 대화를 읽는 창구는 **만들지 않는다**(감사 로그의 「누가 누구에게 언제」 만). 필요하면 별도 결정.

## 6. 데이터 모델(초안)

`community.conversations`(id, kind='direct', created_at) · `community.conversation_members`(conversation_id, user_id, last_read_at) · `community.messages`(id, conversation_id, author_id, body_json, created_at, hidden_at, hidden_by). 1:1 은 (작은 id, 큰 id) 쌍에 유일 인덱스 — 같은 두 사람의 대화는 하나.

## 7. 화면(초안 — DESIGN.md 규칙)

- 커뮤니티 사이드바에 「쪽지」 항목 → 왼쪽 사람 목록(이름 · 안 읽은 수) · 오른쪽 대화창(위로 스크롤하면 이전 글) · 아래 입력줄(Enter 보냄 · Shift+Enter 줄바꿈). 폰은 목록 → 대화 두 화면.
- 사람 이름은 어디서나(글 멘션 · 댓글 작성자) 누르면 「쪽지 보내기」가 나온다 — 사용자 말 「이름을 기반으로 보여지고 클릭하면」.

## 8. 결정할 것 (사용자)

1. 실시간 정도: **A 폴링(기본안)** / B SSE / C WebSocket
2. 1:1 만으로 시작하나, 팀 방까지 첫 판에 넣나
3. 읽음 표시를 상대에게 보이나
4. 손님 계정은 메신저 없음으로 두나
5. 비서 첫 판 범위: 「보내기 + 풍선 알림」까지인가, 비서 안 대화창까지인가
6. 단계 번호: 커뮤니티 로드맵의 몇 단계로 넣나(제안: 커뮤니티 14단계 「쪽지」, 사이트 Q:F-11) — 지금 8~13단계 계획 글 뒤

결정이 오면 커뮤니티 PRD 5장·7장·8장에 옮기고, 그때 지시서를 쓴다.
