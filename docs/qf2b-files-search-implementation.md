## 3. 결정 — 지시서가 비워 둔 곳

| # | 결정 | 왜 |
|---|---|---|
| B-1 | **ILIKE 를 그대로 두고 색인은 「후보 좁히기」로만** | 이름·설명에 검색어(원문)가 들어 있으면 검색어의 한글 조각은 모두 그 행의 벡터에 있다 → 색인 조건은 결과를 줄이지 않는다. 결과·`total` 을 지금과 **같게** 지키는 가장 짧은 길(파일 창구는 검색어를 통째로 한 번 ILIKE — 커뮤니티처럼 낱말로 나누지 않는다. 그 뜻을 바꾸지 않았다) |
| B-2 | **`OR f.search_tsv IS NULL` + NULL 부분 색인** | 채우기 전 행(반영 순서 ②→③ 사이 · 색인을 모르는 길로 들어온 행)도 검색에서 빠지지 않게. 다 채우면 부분 색인은 비어 있어 비용이 거의 0 이고, 플래너는 BitmapOr(GIN + 부분 색인)로 받는다(5장 EXPLAIN) |
| B-3 | **분리 자모(NFD)가 든 검색어는 색인을 쓰지 않는다** | ILIKE 는 원문(분리 자모)끼리 비교하는데 조각은 조합(NFC) 뒤에 만든다. 검색어 끝이 「초성+중성」이고 파일에서는 그 뒤 받침과 한 음절이면 조각이 달라져 색인이 ILIKE 로는 걸리는 파일을 떨어뜨릴 수 있다. 화면은 NFC 로 보내므로(지시서 2.5) 이 길은 프로그램 요청뿐 — 지금과 같은 ILIKE 로 둔다 |
| B-4 | 휴지통 행도 채운다 | 되살리면 곧바로 찾혀야 한다(Q:F-2 배치와 같은 판단). 목록 조건(`deleted_at IS NULL`)은 권한 조건절 안 그대로 |
| B-5 | 새 권한 코드 0 | `Authz::visibleFilesWhere`·폴더 관문(`decideRead`)·ORDER BY 허용 목록 그대로. 새 조건은 값 바인딩(`:q_tq` — 한글 음절 토큰을 ` & ` 로 이은 것뿐, `SearchText::tsquery`) |
| B-6 | `count(*)` 는 그대로 | U-2 가 「개수 세기가 절반쯤」이라 했지만 `total` 은 화면 쪽수의 근거다. 개수 문장도 같은 색인 조건을 받아 함께 빨라진다(바꾸지 않고) |
| B-7 | **파일 색인은 조합 토큰 ∪ 원문 토큰**(`SearchText::indexTextFile` — 독립 검토 M-1) | 파일 창구는 원문 ILIKE 로 다시 확인한다. 저장된 이름·설명에 「조합 음절 + 받침 자모」(LV+T — 「가」+U+11A8)가 있으면 원문에는 「가」가 있는데 조합하면 「각」만 남아 색인이 그 파일을 떨어뜨렸다(검토자가 합성 데이터로 끝까지 재현 — 배치 뒤 어긋남 16). 원문 토큰을 합치면 「검색어(분리 자모 없음 — B-3)가 원문의 부분 문자열이면 그 조각은 모두 벡터에 있다」가 성립한다. 커뮤니티는 조합 뜻(NFC)으로 다시 확인하므로 `indexText` 그대로 — 기본 동작은 바이트 단위로 같다(옛·새 판 차등 6,748묶음 · 다름 0) |

- 새 칸이 표를 넓혀 영문 전수 검색을 늦추는가 — 따로 잼(같은 합성 10만 행, 칸 없는 표 15MB · 있는 표 46MB, 7회 중앙): 개수 307 → 341ms · 307 → 329ms, 목록 406 → 246ms · 312 → 253ms. **흔들림 범위 — 늦추지 않는다**(전수 ILIKE 의 비용은 행 폭보다 글자 비교).
