t-box STAGES 1장과 같다. 이 앱만의 추가: 모든 검토에 **t-box 회귀**(`/var/www/tbox-v2/tests/stage26.sh`·`help_button.sh`)와 `community_app` 권한 부정 확인(T-5), `tbox_backup` 으로 `pg_dump -s tbox_re` 성공(T-6)을 넣는다. 사용자 최소 명령:

```bash
curl -s http://127.0.0.1:8083/api/health                                   # 200 {"status":"ok","db":"ok",…}
sudo -u postgres psql -d tbox_re -c "\dt community.*"                       # 5표 (sessions·audit_logs·boards·posts·comments)
sudo -u postgres psql -d tbox_re -c "\dp public.users" | grep community_app # SELECT + UPDATE(3열) 만
sudo tail -n 5 /var/log/community/audit.log
```

## 4-D단계 — 상태 · 담당자 칸 (2026-09-23 구현)

지시서 `stage4d-status-assignee-directive.md`. 4단계의 **마지막 조각**이다. 데이터베이스
(F-27, 6단계) 전에 **고정 속성 둘**만 페이지에 붙인다 — 사용자 결정 2026-09-22 「⑤는
상태·담당자 먼저」(PRD 11-1 ⑤).

규칙 둘이 이 조각의 전부다.
1. **담당자 후보는 그 페이지를 볼 수 있는 사람뿐이다.** 「누구를 담당자로 고를 수 있나」와
   「누가 이 페이지를 볼 수 있나」는 같은 물음이다. 후보가 그보다 넓으면 볼 수 없는 사람의
   계정명이 새고, 앉혀 봐야 그 사람은 자기 이름이 붙은 페이지를 열 수 없다.
2. **바꾼 일은 지울 수 없다** (C:S-14). `page_property_events` 는 앱 계정에 SELECT·INSERT 만.

**마이그레이션 하나** — `db/migrations/2026-09-23_community_page_properties.sql`
(`pages.status` CHECK 5값 · `pages.assignee_id` → `public.users` · 표
`page_property_events` · 인덱스 둘). **표·열 삭제 0**, 여러 번 돌려도 같다.
Opus 는 임시 DB 에서만 적용해 확인하고 지웠다 — 운영 적용은 메인 세션이 한다.
★ **4-C 와 달리 이 마이그레이션은 코드의 전제다**(런타임이 새 칸을 읽고 쓴다). 순서는
**마이그레이션 → `db/community/grants.sql` → 코드 배포**이고, 새 표에 권한을 주는 것은
`grants.sql` 뿐이므로 두 파일을 함께 돌려야 한다.
