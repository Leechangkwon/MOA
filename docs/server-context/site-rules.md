# CLAUDE.md — Qaredi 작업 지침 (사이트 공통, 한 벌)

**Qaredi** 는 사내 사이트다. 이름은 사용자(이창권)의 이름을 암호화했을 때 나온 문자열이며 「내 것」이라는 워터마크다 — 브랜드로 존중해 쓴다.
한 앱·한 로그인이고, 첫 화면은 **앱 런처**다. 폴더 구조(사용자 결정 2026-09-22): **이 폴더 `/var/www/qaredi/` = 공통 지침·공통 기획**, `tbox-v2/` = t-box 모듈이자 웹 앱 본체(원격 `T-Box_Re`, 자기 git), `community/` = 커뮤니티 모듈 기획안(코드는 다음 단계). 안에 **모듈**이 있다:
**t-box**(파일 공유 — 교육용으로 일부러 취약하게 만든 옛 t-box 를 「뚫리지 않는 형태」로 재구축한 것, 완성·운영 중) ·
**커뮤니티**(블록 기반 개인 업무 공간·게시판·인계 — 기획 완료, 구현 전) · (뒤에 늘어남).
이 파일은 사이트 전체의 **지침 한 벌**이다(하위 폴더에서 시작한 세션에도 상위 폴더 지침으로 자동 로드된다). 모듈 고유 규칙은 각 모듈 폴더의 `CLAUDE.md` 에, 요구사항·설계·이력은 모듈 폴더 안에 있고 지침이 아니라 **참조 문서**다.
장 번호(0~9)는 t-box 시절의 것을 그대로 두었다 — 코드 주석·시험·위키가 「CLAUDE.md 3장」처럼 번호로 인용한다.

- 요구사항 ID 는 모듈 접두로 갈라 쓴다: `T:F-26`(t-box) · `C:F-15`(커뮤니티) · `Q:F-1`(사이트 공통·런처). 한 모듈 문서 안에서는 접두를 생략해도 된다. 지시·보고에는 관련 ID(`S-02`, `T-05`, `R-01` …)를 붙인다.
- **판단 기준**(사용자 지적 2026-09-22): 「노션에 있나」「t-box 에 있었나」가 아니라 **「우리가 쓰기에 더 좋은가」**. **필요·불필요의 판단은 사용자가 한다.** Fable 은 선택지·이점·비용·의견을 나란히 놓는 것까지가 역할이며 「없앤다」「안 넣는다」를 혼자 정하지 않는다. 확인 질문 하나가 잘못 읽고 만든 작업보다 싸다(2026-09-21 「커뮤니티를 추가」 오독 사례) — 갈림길은 묻는다.
- **기획이 끝나기 전에 구현·통합 지시서를 쓰지 않는다**(사용자 지시 2026-09-22).

## 1. 역할 분담 — 어느 모델이 무엇을 하나

| 단계 | 담당 | 실행 방법 |
|---|---|---|
| 기획 · 설계 · 문서 · 검토 · 커밋 | **Fable** (메인 세션) | 직접 수행. 구현 코드는 쓰지 않는다(예외 5장) |
| 구현 (코드 작성·수정) | **Opus** | `Agent` 도구, `model: "opus"`, `subagent_type: "general-purpose"` — 2장 형식 지시서 필수 |
| 구현 후 보안 검토 | **Fable** | 구현 에이전트와 **다른 컨텍스트**에서(3장) |
| 자기 공격(관문 ③) | **사용자** | Fable 이 대신하지 않는다 |

규칙
- 이 세션은 **Fable 로 실행**한다(`/model` 로 확인). 세션이 Fable 이 아니면 작업 시작 전에 사용자에게 알린다.
- 검토는 구현 컨텍스트를 상속하는 `fork` 로 하지 않는다(구현자의 가정을 물려받으면 「추정하지 않는 검토」가 불가능하다).
- **다른 Claude 세션이 같은 저장소에서 일한다.** 시작할 때 `git status` 로 남의 변경을 확인하고, 파일 단위 덮어쓰기(`git checkout -- .` 등)를 하지 않으며, 커밋은 `git add -p` 로 자기 hunk 만 고른다. 문서 경로·공유 파일을 바꿀 때는 그 세션들에 먼저 알린다.


## 3. 구현 후 보안 검토 규칙 (Fable)

**추정하지 않는다. 실행해서 확인한다.**

| 순서 | 할 일 |
|---|---|
| 1 | `SECURITY.md` 4장 절차를 따른다. 변경이 영향을 주는 `T-xx` 는 **전부 실제로 실행**한다(`curl`, `psql`, 브라우저). |
| 2 | `scripts/security_lint.sh` 를 실행한다(저장소 전체). 0건이 아니면 실패. |
| 3 | 실행하지 못한 항목은 **「미검증」**으로 적는다. 미검증을 「안전」이라고 쓰지 않는다. |
| 4 | 보고는 반드시 네 부분: **① 안전한 이유(증거) ② 불안전한 이유 ③ 미검증 ④ 다음 조치** |
| 5 | `SECURITY.md` 7장 검토 이력에 한 줄, 영향받은 R-xx 상태(✅/◐/❌) 갱신, 새 위험은 R-xx(커뮤니티는 `C:R-xx`). |
| 6 | 실패 항목이 있으면 **커밋하지 않고** 2장 형식으로 재지시. 같은 항목 최대 3회, 그 뒤엔 사용자 판단. |
| 7 | 한 모듈을 고쳐도 **다른 모듈의 회귀**를 함께 돌린다(t-box: `tests/stage26.sh` 등, 통합 E 뒤에는 `tests/<모듈>/`). 회귀는 3.1 의 단위로 — 조각마다 전체를 되풀이하지 않는다. |

### 3.1 검토·회귀·반영의 단위 — 기능 묶음 (사용자 결정 2026-09-28)

한 기능이 여러 조각(예: G-0 권한 바닥 → G-1 페이지 폴더 → G-2 기공료 검토 흐름)으로 나뉘어도 **검토·회귀·운영 반영은 기능 묶음 끝에 한 번**이다. 조각마다 같은 옛 시험과 반영 준비를 되풀이하지 않는다.

| 때 | 할 일 |
|---|---|
| 조각마다 | 그 조각의 **수락 시험** + 바뀐 파일에 닿는 시험만(카탈로그 `covers` 가 겹치는 것) + 정적 검사(`security_lint`·부품 버전·위키) |
| 묶음 끝 | 묶음 전체 diff 로 **독립 검토 한 번**(위 1~6) · 묶음이 바꾼 파일과 `covers` 가 겹치는 시험 전부로 **회귀 한 번** · 반영 스크립트·모의 반영·운영 반영 한 번 |
| 예외 — 보안 바닥 | 뒤 조각이 기대는 판정 함수·권한 모델·스키마 같은 바닥은 **먼저 검토만** 받아 둔다(구멍이 늦게 드러나면 위 조각을 다시 고쳐야 한다). 반영은 묶음과 함께 |
| 예외 — 따로 쓰이는 것 | 기능 묶음과 무관하고 사용자가 바로 쓰는 개선(사용감 라운드 · 핫픽스)은 그 자체로 한 묶음 — 따로 검토·반영한다 |
| 가끔 | 카탈로그의 임시 인스턴스·정적 시험 **전부**(운영을 치는 시험 제외)는 큰 발행 전이나 사이트가 한산할 때 |

점검 봇용 기록(첫 수락 직전 `selftest-base/<항목>` · 검토 직전 `review-base/<항목>` 태그와 번들 · 검토 반영은 새 커밋으로)은 몇 초면 되니 묶음 단위로 계속 남긴다. 봇 때문에 검토를 조각마다 따로 받지는 않는다.

검토용 요청은 **검토 계정 `claude_` 5개(`claude_admin01` 등, t-box F-71 — 판정은 `tbox-v2/tests/lib/review_accounts.sh` 한 곳)로만** — 옛 `qa_` 계정은 사용자 결정(2026-09-24)으로 꺼졌으니 옛 시험은 고칠 때 `claude_` 로 옮긴다, 반드시 `-A "tbox-review/$(date +%F)"` 를 붙여 보낸다(표식 문자열은 사이트 공통으로 이것 하나 — `src/Http.php`·시험 스크립트가 같은 값을 쓴다). 시드 계정(`admin01` 등)은 사용자의 자기 공격 전용이라 Fable·Opus 는 쓰지 않는다 — 감사 로그에서 `actor_name`·`user_agent` 만 보고 사용자의 행동과 검토 요청이 갈라져야 한다(t-box PRD S-07, ARCH 4.0). Opus 구현 에이전트의 자체 시험도 같다.

증거의 기준: 「코드를 읽어보니 안전할 것 같다」는 증거가 아니다. **명령 + 응답 원문**(HTTP 상태·본문, SQL 결과)이 증거다.

## 4. 구현 규칙 (Opus 에이전트에도 그대로 적용)

- `tbox-v2/ARCHITECTURE.md` 13장 체크리스트(5대 방어)를 완료 전에 스스로 점검한다. 방어는 모듈을 가리지 않는다: 라우트 정책 필수 · 행 단위 `Authz` 판정 · 목록은 SQL `WHERE` · Prepared Statement 만 · 출력은 `textContent`/`htmlspecialchars` · 외부 요청은 `src/Fetch.php` 한 곳 · CSRF · 감사 기록.
- **보안 핵심 파일**은 지시서의 「수정 파일」에 명시된 경우에만 고친다:
  `src/Authz.php`, `src/Auth.php`, `src/Db.php`, `src/Http.php`, `src/Storage.php`, `src/Upload.php`, `src/Audit.php`, `src/Doc.php`(커뮤니티),
  `db/**`, `deploy/**`, `public/index.php`(라우트 테이블)
- 새 외부 요청 코드(HTTP 클라이언트, 소켓)는 만들지 않는다. 필요하면 멈추고 S-05 심사를 요청한다.
- **본문은 블록 JSON 만 저장한다**(브라우저 HTML 저장 0). 스키마 `community/doc-schema.json` 이 검증기·에디터·렌더러의 공통 진실.
- 외부 코드는 `deploy/DEPENDENCIES.md` 에 버전·라이선스·sha256 을 적은 것만(현재 예외 후보: ProseMirror). CDN 금지, 저장소 안 고정.
- 비밀 정보(`.env`, 인증서, 키)는 저장소에 넣지 않는다. 예시는 `.env.example` 만.
- 완료 보고는 2장의 「보고 형식」을 따른다. 테스트를 돌리지 못했으면 돌리지 못했다고 쓴다.
- **운영 반영은 메인 에이전트가 직접 수행한다**(사용자 결정 2026-10-01 — 「남은 단계 전부 진행하고 사용자 운영 배포 지침을 삭제한 뒤 직접 전부 진행」). 승인된 기능의 DB 마이그레이션·필요한 시스템 설정·cron·코드 배포·서비스 재시작과 배포 후 검증까지 완료한다. 구현 에이전트는 격리 환경에서 구현·시험하고, 메인 에이전트는 독립 검토·백업·모의 적용·드리프트 확인을 마친 뒤 운영에 반영한다. 지시서의 기존 「사용자가 운영 적용」「사용자 몫 서버 설정」 문구는 이 결정으로 대체하며 반복 승인을 요청하지 않는다. `git add -A` 및 시드 계정 사용 금지와 기존 업무 데이터 보존 규칙은 유지한다.
- **운영 데이터에 손대지 않는다(2026-09-11 사고 후 추가)**: 계정·파일·표가 사라졌거나 로그인이 안 되는 등 이상을 발견하면 **멈추고 보고**한다. 시드 재생성·`DELETE`·`TRUNCATE`·`restore`·백업 복원을 스스로 실행하지 않는다 — 증거를 흐리고(06:55 재시드 사례) 복구 판단은 사용자 몫이다. 예외 없음.

## 5. 경미한 변경 (위임·검토 생략 가능)

문서 오탈자, 주석, 로그 문구, CSS 만 바뀌는 변경은 Fable 이 직접 고쳐도 된다.
**단, 4장의 보안 핵심 파일과 권한·SQL·출력·파일경로·스키마 로직은 한 글자라도 경미한 변경이 아니다.**
**문자열 치환 편집 뒤에는 반드시 `php -l`**(2026-09-22 `/**` 손상 사례).

## 6. 진행 단위와 커밋 — 과제 방식

작업 단위는 로드맵의 단계다 — 사이트 `PRD.md` 7장(Q-n) · t-box `tbox-v2/PRD.md` 13장 · 커뮤니티 `community/PRD.md` 11장. 한 단계 = 기능 하나 = 커밋 하나. 한 기능이 조각 여럿이면 관문 ②·④ 와 운영 반영은 **기능 묶음 끝에 한 번**이다(3.1).

| 관문 | 담당 | 통과 조건 |
|---|---|---|
| ① 구현 | Opus | 지시서 범위 완료, 보고 형식 준수 |
| ② 검토 | Fable | 3장 절차, 관련 T-xx 실행 증거 |
| ③ 자기 공격 | **사용자** | 「직접 해볼 공격」을 수행해 막힘을 확인. **Fable 은 이 단계를 대신하지 않는다** — 사용자가 확인했다고 말하기 전엔 다음 관문으로 가지 않는다 |
| ④ 커밋 | Fable | 아래 규칙 |

**일괄 진행 모드(t-box, 사용자 결정 2026-09-11)** — ① 구현 → ② 검토 → ④ 커밋 순으로 멈추지 않고 이어 가고, 관문 ③은 사용자가 뒤에 일괄 수행한다. 이 모드에서는 ② 통과가 커밋 조건이고, ③ 결과는 커밋 뒤 `SECURITY.md` 7장·해당 STAGES 에 추가 기록한다(실패 시 보정 커밋).

- 커밋 메시지는 **한글**, 첫 줄은 `<모듈> N단계: 무엇을`(예: `t-box 4단계: 서버 인가 — …`, `커뮤니티 3단계: …`, `Qaredi A: …`). 본문에 실행한 T-xx 와 결과.
- 커밋 전 `SECURITY.md` 7장 이력에 한 줄(단계, 실행한 공격, 결과). 커밋 전 해당 `STAGES.md`(사이트 또는 모듈)를 갱신한다 — 상태·체크 결과·커밋 해시·학습 기록(9장). **갱신 없이는 커밋하지 않는다.**
- `main` 에 직접 커밋. 원격 `origin`(git2.tla.so `T-Box_Re`, 사용자 결정 Q-A 2026-09-22 「저장소 유지」)에 단계 커밋마다 push.
- `git add -A` 금지. 파일을 지정해서 추가한다(비밀 정보 실수 커밋 방지). `.env` 가 스테이징에 보이면 즉시 중단. 루트의 `jar`·`api-test.txt` 는 커밋하지 않는다(세션 토큰).
- **버전과 발행(F-47)** — 사이트 하나로 `X.Y.Z`: X 대규모 · Y 중규모 · Z 작은 것. 진실은 `VERSION`·`CHANGELOG.json`, `CHANGELOG.md` 는 생성 파일. 사용자에게 보이는 것이 바뀐 커밋(관문 ④) 뒤에 바로 `scripts/release.sh <major|minor|patch> "제목" "무엇이 변했나…"`. 새 화면·새 기능은 minor, **major 는 사용자가 말했을 때만** — 런처가 뜨는 발행은 **v2.0.0 「Qaredi」**(사용자 결정 2026-09-22). 변경 문장은 **사용자 말**로(T-xx·R-xx·파일 이름·「서버가…」 금지). 문서만 바뀐 커밋은 발행하지 않는다.
- (t-box 이력) 3단계는 의도적으로 「권한 검사 없는」 상태로 커밋했다 — 4단계 전후 비교가 과제의 핵심. 라우트 정책 `authenticated` 는 3단계에도 필수였다.

## 9. 단계별 점검표와 학습 기록 — `STAGES.md` 기록 의무 (2026-09-10 추가)

`STAGES.md`(사이트) 와 `tbox-v2/STAGES.md`·`community/STAGES.md`(모듈)는 단계별 **개발 사항 · 체크사항 · 학습 기록**의 장부다. 사용자가 단계마다 스스로 점검할 수 있게 하는 것이 목적이며, 다음은 권고가 아니라 **의무**다. 사이트 공통(런처·통합·이름·문서 구조)은 루트, 모듈 안의 일은 그 모듈 STAGES 에 적는다.

| 무엇을 | 언제 | 어디에 |
|---|---|---|
| 사용자가 **어려워한 부분**(막힌 명령, 이해가 안 된 개념, 실패한 시도) | 그 대화에서 답한 직후 | 해당 단계 「학습 기록」 표, 구분 `어려움` |
| 사용자가 **궁금해한 점**(질문 원문의 요지) | 답한 직후 | 같은 표, 구분 `궁금` |
| **해소된 점**(답의 요지 + 근거 문서 위치 + 확인 명령) | 답한 직후 | 같은 표 「해소·근거」 칸 |
| 사용자의 **결정·요청·지적** | 답한 직후 | 같은 표, 구분 `결정`·`요청`·`지적` |
| 단계와 무관한 **기초 질문**(터미널·리눅스·git) | 답한 직후 | `tbox-v2/STAGES.md` 3장 기초 기록 |
| **보안 점검 방식**의 변화 | 바뀐 그 단계에서 | 해당 STAGES 1장 |
| 관문 ② 검토 결과, 관문 ③ 사용자 결과, 커밋 해시 | 결과가 나온 직후 · 커밋 직전 | 해당 단계 체크 표 + 0장 현황 표 |

규칙
- 형식은 한 줄: `날짜 | 구분 | 내용 | 해소·근거`. 답을 다시 길게 쓰지 않고 **근거 문서의 위치**를 가리킨다.
- 사용자의 말은 **요지 그대로** 적는다. 감정·평가를 덧붙이지 않는다. 사용자가 확인하지 않은 항목을 「통과」라고 쓰지 않는다(`미보고`·`대기`로 남긴다).
- 세션이 바뀌어도 이어지도록 기록은 **파일에** 남긴다. 이전 기록이 없으면 「기록 없음」이라고 적고 지어내지 않는다.
- 관문 ④ 커밋 전 점검에 STAGES 갱신 여부를 포함한다(6장). **t-box·커뮤니티·사이트 단계 모두** 끝나는 커밋에는 **해당 책(`wiki/tbox|community|qaredi/`)의 단계 글과 그 책 `index.json` 갱신·`php scripts/wiki_check.php` 0건**도 포함한다(2026-09-13 사고, 2026-09-23 확대 — 검사가 STAGES 0장의 ✅ 단계와 글을 대조해 빠진 글을 실패로 잡는다, 사용자 승인). `Wiki::STAGE_MAX` 는 t-box PRD 로드맵 끝과 같게 유지한다. 새 단계를 시작할 때는 그 단계의 「개발 사항」 체크리스트를 지시서와 함께 먼저 적는다.
