# 모아 공간과 커스텀 대시보드 — 제품·구조 계획

2026-10-11 사용자 결정: 회사 업무와 모임 모두 지원. 개인 홈과 공간 홈의 커스텀 대시보드 진행 승인. 이 문서는 목표 구조와 구현 단계를 구분한다.

## 1. 브랜드와 서비스

- 이름: 모아. 대표 문구 제안: 함께하는 모든 순간, 모아.
- 정체성: 함께하는 사람들의 자료·활동·기록을 연결하는 그룹 공간.
- 회사와 모임은 같은 공간 모델을 사용한다. 회사에서는 활동을 업무로 표현할 수 있지만 데이터와 권한을 두 제품으로 갈라 만들지 않는다.
- 공통 메뉴: 홈 / 자료 / 활동 / 이야기 / 멤버. AI는 문서·자료·작성 과정에서 도움을 제공하고 PC 연결은 설정과 안내에 둔다.
- 자료실은 t-box가 맡는다. 실제 Google Drive 연동은 이번 범위가 아니다.

## 2. 현재 코드와 목표 구조의 차이

확인한 근거: `src/community/handlers/spaces_list.php`, `src/community/routes.php` 공간 관문, `src/community/CommunityAuthz.php`, `db/community/schema.sql`, `src/community/handlers/groups.php`, `public/assets/community/dashboard.js`.

| 현재 | 의미 | 목표와 다른 점 |
|---|---|---|
| `users.team_id` | 계정의 유효 팀 하나 | 여러 회사·모임 참여를 표현하지 못함 |
| `community.spaces` | personal/team/board 문서 컨테이너 | 통합 서비스 전체의 회사·모임 경계가 아님 |
| `community.share_groups` | 여러 사람에게 문서를 공유하는 그룹 | 자료·활동·이야기 전체를 격리하는 공간이 아님 |
| 기존 문서 dashboard | DB 뷰를 모은 문서와 필터 | 개인/공간 홈 위젯 편집과 목적이 다름 |
| 런처 최근·즐겨찾기 | 기존 권한을 거친 개인 자료·문서 조회 | 공간별 필터·공유 홈의 원천으로 그대로 쓰면 안 됨 |

기존 컨테이너나 공유 그룹에 새 이름만 붙여 다중 공간을 구현했다고 하지 않는다. `/api/spaces`는 팀 컨테이너를 생성할 수 있는 GET이므로 대시보드의 순수 조회로 취급하지 않는다.

## 3. 목표 공간 모델 — 아직 미구현

`product_spaces`(가칭): UUID, 이름, 유형 company/group, 상태 active/archived, 소유자, 생성·수정 시각. 유형은 기본 홈 구성을 고르는 메타데이터이며 권한 근거가 아니다.

`space_memberships`(가칭): space_id + user_id 고유, 역할 owner/admin/editor/member/viewer, 활성·탈퇴 상태. 사용자는 여러 공간에 참여 가능. 글로벌 계정 역할과 공간 역할을 분리하고 유효 권한은 둘의 제약을 모두 적용한다. 회사 공간의 관리자는 다른 모임의 관리자가 아니다. 마지막 소유자 제거는 금지한다.

`space_invites`(가칭): 해시로 저장한 초대 비밀, 만료, 횟수 제한, 부여 역할, 발급자, 취소. 초대 화면은 대상 공간의 필요한 소개만 보여준다. 소유권 이전은 별도 재인증과 감사 절차를 거친다.

활동·자료·이야기는 명시적인 공간 연결을 갖는다. 기존 데이터는 기존 범위로 보존하고 새 공간에 자동 공개하지 않는다. 여러 공간의 파일 재사용은 단순 링크로 권한을 넓히지 않으며 원본 권한과 목적지 정책을 함께 검사한다. 공간 삭제는 즉시 원본 삭제로 이어지지 않는다.

## 4. 홈과 위젯

| 홈 | 읽는 데이터 | 배치 편집 |
|---|---|---|
| 내 홈 | 본인이 현재 열 수 있는 정보 | 본인 |
| 공간 홈 | 해당 공간 안에서 열 수 있는 정보 | owner/admin 또는 명시적 홈 편집 권한 |

회사 기본 홈: 공지 / 내 작업 / 프로젝트 현황 / 최근 자료. 모임 기본 홈: 다음 일정 / 준비할 일 / 공지 / 새 이야기. 기본 템플릿은 표현 배치만 바꾸며 권한이나 실제 데이터를 만들지 않는다.

위젯 카탈로그 목표: 공지, 할 일, 일정, 자료, 이야기, 바로가기. 첫 개인 홈 구현은 현재 런처가 제공하는 서비스·최근 작업/즐겨찾기·연락과 안내·읽을거리 영역을 조합한다. 공지·일정·공간별 작업 집계는 이후 공간 API 단계에 구현한다. 빈 상태와 실패 상태는 실제 상태를 표시하고 샘플 수치·게시물로 채우지 않는다.

위젯 설정은 종류·순서·표시 여부·폭·허용된 소스 선택이다. HTML/JS/CSS 실행이나 임의 API URL 입력은 제공하지 않는다. 제목 등 원천 데이터는 배치 설정에 복제하지 않는다. 모바일은 한 열이고 조작은 터치와 키보드 모두 지원한다.

## 5. 저장과 동작 규칙

- 1차 개인 홈: 계정별 브라우저 localStorage에 검증된 배치 설정만 저장. 내용·사진·메시지·API 응답·인증 정보는 저장하지 않는다. 화면에 브라우저 한정 저장을 표시한다. 다른 기기 동기화와 공동 편집은 미지원이다.
- 이후 서버 저장: 개인 홈 user_id와 공간 홈 space_id를 분리한다. 버전 있는 JSON 스키마와 설정 크기·위젯 수 제한을 둔다. 변경에는 CSRF·행 권한·감사를 적용한다. revision/ETag 충돌로 다른 편집자의 설정 덮어쓰기를 방지한다.
- 편집은 초안 → 저장/취소. 기본값 복원도 초안에서 진행한다. 저장 실패 때 저장 성공을 표시하지 않는다.
- 위젯 숨김은 원본 자료 삭제가 아니다. 배치에 위젯 ID나 공간 ID가 있어도 서버 권한을 대신하지 않는다.
- 공간 전환/계정 변경/탈퇴·로그아웃·권한 오류에 과거 응답을 지우고 요청 세대 번호로 늦은 응답을 차단한다. 캐시·집계·검색·파일 다운로드도 같은 공간 경계를 검사한다.

## 6. 구현 순서와 완료 기준

1. **개인 홈 편집**: 기존 실제 데이터·권한 유지, 위젯 표시/순서/폭/최근·즐겨찾기 및 자료·문서 선택, 저장/취소/복원, 모바일·키보드 검사. 운영 반영은 별도 검증 뒤 진행.
2. **공간 권한 바닥**: 다중 멤버십·역할·초대·보관·소유권 이전. 이전 데이터 비공개 보존과 다른 공간 UUID/집계/다운로드 격리 검사 후 다음 단계 진행.
3. **공간의 자료·활동·이야기 연결**: 목록·검색·API·본문·첨부·AI 요청까지 같은 경계. 기존 파일과 문서의 명시적 이전/연결 및 실패 롤백 정책 검증.
4. **공간 홈과 원천 위젯**: 실제 공지/할 일/일정/자료/이야기 조회, 열람 권한별 집계, 회사·모임 기본 템플릿. 공동 설정 서버 저장·동시 편집·멤버 제거 즉시 반영 검사.
5. **개인 홈 동기화와 서비스 안내**: 여러 공간의 내 작업을 권한에 맞게 모아 보기, 기기 동기화, 시작 안내. 같은 사람의 회사·모임 흐름을 실제로 확인.

## 7. 운영과 검증

합성 데이터·격리 DB에서 서로 다른 두 공간과 복수 역할을 검사한다. 운영 계정·파일·사진을 테스트용으로 복제하거나 재시드하지 않는다. 기존 Authz/CommunityAuthz와 목록 SQL 원칙은 보존하고 새 경계의 중앙 판정 함수를 설계한다. 글로벌 관리자의 예외 열람 여부는 감사·조직 정책을 포함해 별도 확정한다.

스키마 단계는 migration/owner·ACL·백업·모의 적용·드리프트/실제 HTTPS·원본 데이터 보존 확인 후 반영한다. Git 커밋·브랜치·스크린샷은 배포 완료의 증거가 아니다. 실제 Google Drive 연동, 과금, 공개 가입, 외부 공개 공간은 이번 승인 범위에서 추가하지 않는다.
